# OmniSlash facts

Checked against main at fbe533c on 2026-11-26.

## What it is
OmniSlash is a command-line tool for keeping track of tickets, projects and the agents that work on them.
It is in alpha, so anything may change or break.

## Today
- `help-command`: `bun apps/cli/src/index.ts --help` prints the grouped command overview from a checkout of main, `<command> --help` and `help <command> [subcommand]` print per-command or per-subcommand help, and `help env` lists environment variables (apps/cli/src/help.ts, apps/cli/src/cli.ts; `bun test test/help-system.test.ts` in apps/cli passes).
- `item-tracking`: with `OMNISLASH_STORE=sqlite`, `OMNISLASH_DB_CREATE=1` and `OMNISLASH_DB` set to a new path, `bun apps/cli/src/index.ts add "<title>" --project <name> --kind side` and `list` create and list work items in that new SQLite file. Postgres is the default store and needs a connection URL.
- `drilled-ticket-gate`: the first dispatch (`spinoff <ticket>`) of a ticket not tagged `spike` is refused, with nothing queued, when the ticket has no `## Drilled` section or no `## Done when` item, and when no `go` check is recorded on the ticket's current text, unless the dispatcher overrides it with `--no-check '<why>'`; a `spike` ticket is refused instead without `## Questions`, `## Box`, `## Done when` and a link to the ticket it serves (platform/cli-coord/src/spinoff-check.ts:352-399; `bun test test/spinoff-drilled-1980.test.ts test/spinoff-check-1825.test.ts` in platform/cli-coord passes).
- `spike-claims-review`: `spinoff handoff` on a `spike` ticket is refused, with the row unmoved and nothing sent, unless its note (or `--report`) carries a `claims-review: <N> cut, 0 open` line; a line with open findings is refused with the open count, and a ticket not tagged `spike` is not checked (platform/cli-coord/src/spinoff-spike.ts, platform/cli-coord/src/commands/spinoff.ts `markSpinoffReady`; `bun test test/spinoff-spike-1826.test.ts` in platform/cli-coord passes).
- `handoff-pixelslash-owed`: with an open PR, `spinoff handoff` refuses a pending or failing check, but a pending status named `PixelSlash` (or starting with it) is a human review, not CI: it is not waited on, the handoff goes through and prints `PixelSlash review owed: <status> <link>` (JSON `pixelslash_review_owed`), and a failed or errored one still refuses; `skills/ob-babysit-pr/scripts/pr-wait <pr> --until green` exits 0 the same way once every other check passed (platform/cli-coord/src/commands/handoff-ci.ts `isPixelSlashCheck`; `bun test test/handoff-ci-2044.test.ts` in platform/cli-coord and `bun test test/pr-wait-pixelslash-2544.test.ts` in platform/cli-core pass).
- `critical-only-usage`: a `critical` priority ranks above urgent (stored as 6). Pacing follows the provider of route `builder.complex`'s first model (the local models file, then the last `model_routes` this machine read): `antigravity` reads `gemini-weekly` from T3 Code's local `~/.t3/caches/antigravity.json`, and anything else (including a missing or malformed models file) reads `seven_day` from `~/.t3/caches/claudeAgent.json` (`OB_USAGE_T3_CACHE` overrides the path); `checkedAt` reads `usageLimits.checkedAt` falling back to top-level `checkedAt`. While that weekly usage is 98% or more and its window has not reset, `next` lists only critical items after one line naming the provider (Gemini for Antigravity, Claude otherwise), usage and reset, and a dispatch, queue or send-back of a ticket that is not critical is refused with nothing queued or changed, unless overridden with `--over-usage '<why>'`, which is recorded on the ticket and refused from a T3 Code thread. A missing cache, no weekly window or a check older than 60 minutes reads as usage unknown, is said once on stderr and never blocks (apps/cli/src/usage-gate.ts, apps/cli/src/commands/usage.ts; `bun test test/usage-gate-os108.test.ts` in platform/cli-core and `bun test test/spinoff-usage-gate.test.ts` in platform/cli-coord pass).
- `parallel-conflict-checks`: a declared-file overlap warning. Before a dispatch launches, the ticket's declared files (its newest `go` check's sheets, directory and glob entries kept) are compared with every live spinoff row in the same repo, that row's declared files plus its pushed branch's `git diff --name-only origin/main...origin/<branch>` (its worktree when not pushed, else declared only). Each overlapping row prints `overlap: <ref> (#<row>) <paths>` and one `overlap` decision is recorded on the ticket, and the dispatch launches anyway; lockfiles are ignored, and with `--no-check` it prints `overlap: unknown, no recorded check`. `spinoff overlap <ticket> [--json]` prints the same lines without launching, over the API on a client (platform/cli-coord/src/spinoff-overlap.ts; `bun test test/spinoff-overlap-os47.test.ts` in platform/cli-coord passes).
- `branch-conflicts`: a test-merge of running builders' branches. `spinoff conflicts [--repo <name>] [--json]` takes every running row (pending, launching, launched, ready-for-gate) with a branch, and per repo with two or more fetches their branches once and runs `git merge-tree --write-tree --name-only` on each pair's `origin/<branch>` heads in this machine's checkout: exit 1 is a conflict, so two branches editing one file at different lines are not reported. It prints `conflict: <ref> (<head>) and <ref> (<head>): <files>` per pair or `conflicts: none`; an unpushed branch, a repo with no checkout here, a conflict only in lockfiles or FACTS.md (resolved at land; a pair with a real file too reports just that file) and two rows of one ticket are skipped, and a git failure warns. `role tick` runs it for each team and posts each pair once per pair of heads (`client_key` `conflict:<rowA>:<headA>:<rowB>:<headB>`) to the team's sentinel, starting one when there is none, and notes both tickets only when that message is new; any failure in the check warns and never fails the tick. It detects only: nothing pauses or rebases a builder (platform/cli-coord/src/spinoff-conflicts.ts, apps/cli/src/commands/role-tick.ts; `bun test test/spinoff-conflicts-os48.test.ts` in platform/cli-coord passes).
- `agent-build-worktree`: a dispatch opens the builder in a git worktree on the ticket's own branch: it reuses the worktree already checked out on that branch, or else runs `git worktree add <path> -b <branch>` from `origin/main` (local `main` when the repo has no `origin/main` or its local `main` is ahead), and launches the builder as a T3 Code thread, the only launcher, so it needs T3 Code (platform/cli-coord/src/commands/spinoff.ts:1195-1209 and 1528-1536).
- `db-clone`: `db clone [--target <db>] [--grant-role <role> | --no-grant] [--dry-run] [--json]` refreshes a test copy of a live Postgres database from this machine, never through the API: it reads a machine-local profile (`OB_DB_CLONE_FILE`, else `~/.config/ob/db-clone.json`) naming the Proxmox container, the clone script, its install path, the live database, protected names, the target and the role to grant; refuses the live database, a protected name, `postgres`, `template*`, the clone's scratch names and reserved roles before anything runs; installs the script in the container (`pct exec` on the Proxmox host, else over ssh to it) only when it is missing or differs; streams the script's output; refuses by name when ssh cannot reach the host; and ends with `ob secret get <urlSecret>`, never a value (apps/cli/src/commands/db-clone.ts; `bun test test/db-clone-os222.test.ts` in apps/cli passes).
- `leases`: a lease on a resource such as `ticket:<ref>` or `worktree:<path>` has one live holder at a time, and a second holder is refused until it is released or expires (platform/cli-coord/src/lease.ts:175-189 and 466-467; `bun apps/cli/src/index.ts lease --help` lists `acquire`, `run` and `release` subcommands; `bun test test/lease.test.ts test/lease-tickets.test.ts` in platform/cli-coord passes).
- `review-merge-skills`: agent skills gate a builder's pull request before merge: `ob-skeptical-review` (read-only reviewers that presume every changed line is wrong; the default leg is `opus` through `claude` on every complexity, with `neon` through `agy` only as its fallback; `deepseek` and `luna` are retired: a models file or `review_readers` that names them drops those entries with an `OS-206` warning and loads the rest, and a command-line leg of either is refused); a leg that fails ends its stderr with `review-leg: <leg> failed: exit <n>: <first line of the tool's stderr>`, which the review line copies as `+ <leg>: failed (exit <n>: <reason>)`, `ob-babysit-pr` (the watch on a handed-off pull request) and `ob-land` (the builder opens the pull request, another role gates and merges it) (skills/README.md:46-48, apps/cli/src/models-file.ts, apps/cli/src/review-readers.ts, skills/ob-skeptical-review/review-leg.ts).
- `gate-file`: each repo declares its gate once in `gate.json` (a list of named steps, each a shell `run` with an optional `env`), and `gate run [--force] [--json]` runs the steps in order in the repo root, without the caller's `OMNISLASH_*` variables as in CI, stopping at the first red step and naming it. The result is cached under the git common dir by the HEAD sha plus the file's hash, so a second run at the same commit and file is a cache hit that runs no step; a dirty worktree runs and is never cached, and a red result is cached too. It needs no tracker, and CI's `gate` job runs `bun apps/cli/src/index.ts gate run` on the same file (apps/cli/src/commands/gate.ts, gate.json, .github/workflows/ci.yml; `bun test test/gate-os210.test.ts` in apps/cli passes).
- `review-run`: `review run <ticket> [--complexity <1-10>] [--answers <file>] [--json]` runs the skeptical review with no agent choosing the steps: it marks the row `reviewing` (best effort), runs the gate and stops on red, runs one reader for round 1, and runs one more reader only when the round-1 leg failed, gave no score, raised a wrong or unproven finding, or scored under 8/10; that extra reader is always an Opus reader (another configured one, else a second seat `opus-2` of the round-1 reader), never `neon`, and the command never runs a reader's fallback. Each leg runs through `review-leg.ts` with a run id, so its record in `review-legs.jsonl` carries its tokens, and one record per round goes to `review-runs.jsonl` beside it with each leg's verdict and tokens. `--answers` runs the next round, giving each leg only its own previous findings and its own `## <leg>` section of the answers (apps/cli/src/review-run.ts; `bun test test/review-run-os210.test.ts` in apps/cli passes).
- `review-leg-antigravity-readonly`: an Antigravity review leg (`neon`) runs `agy` in Default mode with an allow list of `read_file` and anchored regexes for the read-only commands, whose arguments cannot hold shell metacharacters and whose `git` arguments cannot start with `--o` or `-o`; a command outside it is refused, and a run that ends with an empty response is a failed leg. On 2026-11-26 a live leg on a 13-line diff returned findings, wrote nothing past injected write steps and recorded its tokens, and seven direct attacks (`;`, `$()`, a pipe, `>`, `git diff --output=`, `--out=`, `touch`) wrote no file (skills/ob-skeptical-review/review-leg.ts `antigravitySettings`; `bun test test/review-leg-antigravity-os130.test.ts` in platform/cli-core passes).
- `skills-doctor`: `skills doctor` prints one line per symlink in `$HOME/.claude/skills` that points into the omnibus or omnislash checkout (the `repo_checkouts` setting, else `$HOME/dev/<name>`): `<name> <target> same|differs|omnibus-only`, a `differs` line naming which side's last commit on the skill is newer; `--fix` repoints only a `differs` link omnislash is newer on at the omnislash copy and changes nothing else (apps/cli/src/commands/skills.ts; `bun test test/skills-doctor-os182.test.ts` in apps/cli passes).
- `role-state-machine`: the role state machine (20 states and 39 moves from exploring an idea to a closed ticket, each state with its role, whether a human is required and the item or spinoff status it rides on) is defined once in platform/state-machine/src/role.ts, which builds the ten states that mirror a spinoff row status or phase (queued, launching, building, handed_off, failed and the five phases) from the row and phase machines, so a sent-back row, conflicts included, sits on `updating_pr` with the builder, and a handed-off row whose work goes on in the same thread after the owner's call goes back to `building` with no phase through `spinoff resume <row|ticket> --note '<the work that continues>'`, which also clears its recorded verdict, so it leaves the sentinel inbox (platform/cli-coord/src/commands/spinoff.ts `markSpinoffResumed`; `bun test test/spinoff-resume-os235.test.ts` in platform/cli-coord passes); `bunx moon run state-machine:export` writes `docs/role-state-machine.json` (version 1: roles, states, transitions with from, to, label, event, actor and source, a source being a `skills/<name>/SKILL.md:<line>` or the `<path>#<event or function>` that applies the move) and `docs/role-state-machine.mmd`, and CI fails when the committed copies differ from the machine (`-- --check`); a push to main that changes them opens or updates a pull request in slashsuite/slashslash replacing its copies when the `SLASHSLASH_SYNC_TOKEN` Actions secret is set, and does nothing otherwise (platform/state-machine/src/export.ts, .github/workflows/sync-role-state-machine.yml; `bun --bun vitest run` in platform/state-machine passes).
- `role-skills`: agent skills prime a thread for each role: `ob-architect` (plans, drills and dispatches every build, then gates and merges), `ob-sentinel` (verifies, merges and deploys every pull request) and `ob-muse` (explores and hands over a design once confirmed) (skills/README.md:39, 51 and 58).
- `role-runs`: `role start <team> <role>` keeps one T3 Code run per team role (architect, sentinel or muse): it reuses the open run while its thread is live; with no open run and a live seat thread for the role (bound by `t3 architect` or `t3 team restart`) it opens no run and uses the seat as it is, launching, pinning and moving nothing; and otherwise opens a new pinned thread on route `role.<role>` (its default is the active profile's `builder.complex` with a provider, else `claudeAgent:claude-opus-5-5`) at the model's default effort; `t3 architect|sentinel|muse` and `t3 team restart` (`ensureTeamThread`) open new role threads on route `role.<role>` when a models file or `model_routes` names it (else the T3 project's default model); `role status` and `role end` read and end a run. Each run is a row in `role_run`, whose partial unique index on (team, role) where `ended_at` is null keeps one open run (apps/cli/src/commands/role.ts, apps/cli/src/t3/dispatch.ts, apps/cli/src/role-run.ts; `bun test test/role-run.test.ts` in platform/cli-core and `bun test test/t3-dispatch.test.ts` in platform/cli-coord pass).
- `model-routes`: which model runs every use is one server setting, `model_routes`: routes (the builder set, `checker`, `role.architect|sentinel|muse`, `sweep.first`, `sweep.escalate`, `subagent.explore`, `subagent.fixup`, `job.<name>`) each with a fallback chain and an optional effort, grouped into profiles with one `active`. Each route resolves from this machine's `~/.config/ob/models.jsonc`, then the server, then the defaults (what ran before), and `ob models show` labels each `local`, `server` or `default`; a `builder.*` or `role.*` chain entry must be `<provider>:<model>`: `ob models set` and the Models page refuse a bare id there by name (the Models page shows a `claude-*` id in a builder band still on the defaults with `claudeAgent:`, so saving the set as shown goes through), and `ob models show` flags any bare one already stored; `ob models get|set|unset|use|reader` read and write it, over the API on a client. The builder set is ranges of a 1-10 complexity score, `builder.<from>-<to>`, which must cover 1-10 with no gap and no overlap in each layer; the old `builder.simple|medium|complex` routes read as the ranges 1-3, 4-6 and 7-10, a layer mixing both forms is refused, and `role.*` and `job.*` take the range covering 8. A dispatch is scored with `--complexity 1-10` (5 when none is given; `--tier simple|medium|complex` is an alias for 2, 5 and 8 that prints a note, and both flags together exit 2), an urgent ticket runs at `max(score, 7)`, the score is stored on the spinoff row (SQLite and Postgres) and sent over the API (a tier-only client is accepted), `ob spinoff show` and `gateable` print `complexity N/10`, and `ob spinoff trial start --range a-b` pairs only scores in that range. The skeptical-review legs are ranges too: the profile's `review.tiers` is a list of `{from, to, legs}` covering 1-10 with no gap and no overlap (the old `{simple, medium, complex}` object reads as 1-3, 4-6 and 7-10, and ranges that are exactly those bands are still stored in that form so an older `ob` reads them), `ob review readers --complexity <n> -q` prints the legs of the range covering a row's score (`--tier` is an alias for 2, 5 and 8), and `ob review readers range <from-to> <legs...>` and `ob models reader range` set one, carving it out of the ranges it overlaps (`tier` stays an alias for one release). A spinoff launch moves along the chain of the range covering its score only on a credit or quota error, recording `route <name>: <from> -> <to> (quota)` on the ticket's Decisions trail (apps/cli/src/model-routes.ts, apps/cli/src/commands/models.ts, platform/cli-coord/src/spinoff-credit.ts; `bun test test/model-routes-os145.test.ts test/complexity-ranges-os177.test.ts test/review-ranges-os175.test.ts` in platform/cli-core and `bun test test/t3-dispatch.test.ts test/spinoff-urgent-tier.test.ts test/spinoff-trial-1991.test.ts` in platform/cli-coord pass).

The profile's builder ranges and review ranges show as rows of from, to and the models or legs: a row's boundaries, models, effort or legs can be edited, a row split at a score or merged with the next, and the set is saved whole, so a gap or overlap is refused with the same message as the CLI and nothing is stored. Above the review readers it shows the OpenCode Go credit state (ok, running low, failed, or not checked yet) and the time of the last recorded `ob creds check opencode-go` (with its recorded detail when it is not ok), read from the store and never from the provider. - `role-tick`: `role tick` writes what needs each team's architect into its inbox, one message per finding, and delivers it as `send` does: a T3 builder whose heartbeat is over 60 minutes old, a flake ticket with no builder on it, and a team project with nothing in flight whose top item would dispatch today. It also posts each pair of conflicting running branches to the team's sentinel (`branch-conflicts`). An unchanged finding writes nothing again, a pass with no unread message delivers nothing and starts no run, and while the good-night lock file holds a future time it writes but starts and sends nothing. `daemon install` installs it as a client job every 15 minutes (a systemd user timer on Linux, a launchd job on macOS) (apps/cli/src/role-tick.ts, apps/cli/src/commands/role-tick.ts; `bun test test/role-tick.test.ts` in platform/cli-core passes, locally and over the API, and `bun test test/daemon-linux-664.test.ts` in platform/cli-coord passes).
- `role-end`: `role tick` also ends a team's open role runs on this machine's T3 when they are done: a run with nothing for 15 minutes after its last turn, or whose context (read from T3 Code's own state database) has reached 200,000 tokens, is asked to write its successor note with `role note`, then its thread is settled and the run ended, freeing its lease. A turn in flight, a question waiting on the owner or a message queued in the thread keeps it open, and a run that writes no note within 10 minutes is kept (apps/cli/src/role-end.ts, apps/cli/src/commands/role-tick.ts; `bun test test/role-end.test.ts` in platform/cli-core passes).
- `project-status`: a project has a lifecycle status, `active` (the default, and what a project from before migration 0005 reads), `paused` or `archived`, set with `project edit <p> --status <s>` or `project pause|resume|archive <p>`. A ticket in a paused or archived project is refused by `spinoff <ref>`, `spinoff queue <ref>` and the API enqueue with nothing queued and the status named, unless `--allow-paused '<why>'`, whose reason goes on the ticket's Decisions trail bound to that row; `spinoff drain` leaves such a row queued. `next` without `--project`, `role tick` and `role brief`'s next items leave those projects out, and `project list` hides archived ones unless `--all` and prints the status as its last column (`status` in `--json`) (apps/cli/src/project-status.ts, platform/cli-coord/src/spinoff-paused.ts; `bun test test/project-status-134.test.ts` in platform/cli-coord passes).
- `compared-linear`: Linear ships agents on issues: an issue is delegated by assigning it to Linear's own agent or an installed third-party agent, and Linear's agent writes code in a sandbox and creates branches (https://linear.app/docs/agents-in-linear, https://linear.app/docs/assigning-issues and https://linear.app/changelog, read 2026-11-18). Those pages name no check on what an issue says before it is delegated; OmniSlash refuses the first dispatch of a ticket that has no drilled section, no done-when item or no recorded check, unless overridden, as `drilled-ticket-gate` says (platform/cli-coord/src/spinoff-check.ts:352-399). OmniSlash makes no other claim beyond what Linear ships.
- `compared-jira`: Jira ships Rovo agents on work items, in beta: an agent is added to the assignee field, mentioned in a comment, or set on a workflow transition or board column, and the Rovo Dev coding agent has a CLI worktree mode that creates a branch (https://support.atlassian.com/rovo/docs/collaborate-with-your-rovo-agent-on-work-items/ and https://support.atlassian.com/rovo/docs/use-worktree-mode-in-rovo-dev-cli/, read 2026-11-18). Those pages name no check on what a work item says before an agent takes it; OmniSlash refuses the first dispatch of a ticket that has no drilled section, no done-when item or no recorded check, unless overridden, as `drilled-ticket-gate` says (platform/cli-coord/src/spinoff-check.ts:352-399). OmniSlash makes no other claim beyond what Jira ships.
- `scoped-api-token`: `ob api-token add <user> --project <p>[,<p>...]` prints a token once and stores only its sha256 in `~/.ob_api_tokens.json` (`OB_API_TOKENS_FILE` moves it, mode 0600 or every scoped token is refused with the path named); the API re-reads the file per request. A scoped token reaches only the routes marked `scoped` in `OB_API_ROUTES` (`read` for a GET, `write` for any other method) in the families items, next, search, projects, spinoffs, agents, leases, teams and decisions: it can write items, run a spinoff from enqueue to land, register agents, take leases and use a team's role routes and inbox, all filtered to its projects (anything outside them, and any machine slot such as `cpu:browser`, is 404, the same as missing), and the server writes `actor`, `holder`, `by`, `caller` and `from` as the token's user. `DELETE /items/<ref>`, spinoff reclaim, reopen and trial, agent reset, lease sweep, team create, edit, join, leave and delete, decision supersede, every admin family and any unknown path are 403 `forbidden` (apps/cli/src/api/scoped-tokens.ts, apps/cli/src/api/scope-guard.ts, platform/cli-core/test/api-scoped-token-178.test.ts and api-scoped-token-179.test.ts).
- `item-machine`: every item status move (`state`, `close`, `reopen`, `block`, `unblock`, the API `/state` and `/close`) is checked by the item's lifecycle machine in platform/state-machine/src/item.ts; a move the machine does not allow, or a status that is not one of its states, is refused with `item '<ref>' is <from>: 'to:<to>' is not a move from there`, exit 1 on the CLI and 409 over the API, and writes nothing. A block with an empty reason is refused (`a block needs a reason`). `state <id> <to> --repair '<why>'` moves a stuck row to any status of its type but `done` and `blocked`, records `repair: <why>` on the trail, and runs only against a local store (apps/cli/src/workflow.ts; `bun test test/item-machine-os172.test.ts` in platform/cli-core and platform/cli-db passes).
- `spinoff-machine`: every spinoff row move (claim, launch stamp, reclaim, handoff, send-back, land, reopen, retire) is an event of the spinoff machine in platform/state-machine/src/spinoff.ts (`claim`, `stamp`, `retry`, `fail`, `handoff`, `sendback`, `land`, `reopen`), applied by `applyMove` in platform/state-machine/src/apply.ts with a guarded write; a move the machine does not allow from the row's status is refused with `spinoff #<id> is <status>: '<event>' is not a move from there`, exit 1 on the CLI and 409 over the API, and writes nothing. `SPINOFF_TRANSITIONS` is generated from the machine's edges, and a status move on the decisions trail names its event, as in `building → handed-off (handoff, row 12)` (platform/cli-coord/src/commands/spinoff.ts `moveSpinoff`; `bun test test/spinoff-machine-os173.test.ts` in platform/cli-coord passes).
- `spinoff-phase`: a spinoff row stores a role phase inside its status in `spinoff.phase` (migration 0006, null on older rows): `building` holds `reviewing`, `pr_ci` and `updating_pr`, `handed-off` holds `gating` and `owner_merge_call`, and every other status holds none. `spinoff phase <ticket|id> <phase>` moves it through the phase machine in platform/state-machine/src/spinoff-phase.ts, `handoff` sets `gating` (or `owner_merge_call` when the row's `spinoff state` verdict is `needs-human`), `sendback` sets `updating_pr`, a `needs-human` verdict recorded on a handed-off row sets `owner_merge_call` and a later other verdict sets `gating` again, a launch re-stamp keeps it and every other status move clears it. A phase the status does not hold is refused with `spinoff #<id> is <status>: it cannot be in phase '<phase>' (...)`, exit 1 on the CLI and 409 over `POST /spinoffs/phase`, writes nothing to the row and logs a `machine_would_refuse` event. `spinoff list --json`, `spinoff show` and `GET /spinoffs` carry the phase (platform/cli-coord/src/commands/spinoff.ts `setSpinoffPhase`; `bun test test/spinoff-phase-os183.test.ts` in platform/cli-coord passes).
- `spinoff-lifecycle-guards`: every spinoff row write holds to the row's stored status: claim, stamp, handoff, send-back, resume, reopen and land move only by an edge of the spinoff machine, and `spinoff state` records a verdict only on a launching, building or handed-off row, with a write that changes nothing and is refused when the row moved meanwhile. A send-back, a resume and a reopen clear the recorded verdict, and undoing a send-back the builder could not be told of puts it back. `spinoff handoff` on a branch that is not a spike's, with no open PR, is refused when the branch has commits past main (`push the branch and open it ... Nothing was handed off`) and reads `COULD NOT READ CI` when git cannot count them; a branch with none (a scan or measurement run) hands off with `ci: none (no commit past main and no PR: nothing to merge)`, and its readying note tells the sentinel there is nothing to gate or merge. The `## Drilled` and spike section gates read a heading `note` stamped with its `[<time>]` prefix. platform/state-machine/model/Spinoff.tla models the row lifecycle with the machine's edges, `bunx moon run state-machine:tlc` runs TLC on it, and CI's `tla` job runs it on every PR (platform/cli-coord/src/commands/spinoff.ts, platform/cli-coord/src/commands/handoff-ci.ts; `bun test test/spinoff-lifecycle-os211.test.ts test/handoff-ci-2044.test.ts test/spinoff-drilled-1980.test.ts` in platform/cli-coord and `bun --bun vitest run` in platform/state-machine pass).
- `machine-audit`: `ob machine audit [--json] [--since <date>] [--stale-days N]` reads, and never writes, three lists: items and spinoff rows whose status is not a state of their lifecycle machine, spinoff rows in `launching` or `launched` not moved for N days (default 7, oldest first), and the `machine_would_refuse` events (logged by OS-169's shadow before OS-173, and by a refused spinoff phase move since OS-183) since the date (default 7 days back) grouped by machine, from, event and today's answer with a count and the newest example. - `dashboard-machine`: the OB dashboard has a Machine page at `/machine` that draws the role state machine through `fromXState` on `roleMachine` (each state's `meta.role` is its owner, `human_required` marks it a human state) with every in-flight spinoff on the role state it is in: the newest dispatch of each open ticket (one row per trial leg, leg b drawn as `<ref>-b`) that is not merged, not abandoned, and on an open ticket (a mis-dispatched row whose ref is a CLI verb or scratch id names no ticket and is left out). A launched row whose builder is `needs-human` or `blocked` sits on `owner_call`; a handed-off row whose verdict (the recorded one, else the branch's `State:` line when its worktree is on the dashboard's host) is needs-human sits on `owner_merge_call`, a human state; otherwise a stored `phase` names the state, a launched row is `reviewing` while readying, else `building`, and a spike is `spike` until it ends, then `closed`. Every other open ticket in `ob next` order (held projects left out, and a ticket whose newest dispatch merged left out until it is closed) sits on a planning state: tagged `needs-jacobus` on `owner_plan_call`, tagged `idea` on `parked_idea`, with an `ob spinoff check` verdict other than no-go on its current body on `checking`, else on `drilling`; each box's count is every ticket on it and its first dots are the next in that order. Under the diagram each state that holds tickets has a list, its count on the summary, of every ticket by ref and title, each opening the item drawer, and clicking a state's box opens and scrolls to its list.
