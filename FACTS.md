# OmniSlash facts

Checked against main at bceee63 on 2026-11-24.

## What it is
OmniSlash is a command-line tool for keeping track of tickets, projects and the agents that work on them.
It is in alpha, so anything may change or break.

## Today
- `help-command`: `bun apps/cli/src/index.ts --help` prints the grouped command overview from a checkout of main, `<command> --help` and `help <command> [subcommand]` print per-command or per-subcommand help, and `help env` lists environment variables (apps/cli/src/help.ts, apps/cli/src/cli.ts; `bun test test/help-system.test.ts` in apps/cli passes).
- `item-tracking`: with `OMNISLASH_STORE=sqlite`, `OMNISLASH_DB_CREATE=1` and `OMNISLASH_DB` set to a new path, `bun apps/cli/src/index.ts add "<title>" --project <name> --kind side` and `list` create and list work items in that new SQLite file. Postgres is the default store and needs a connection URL.
- `drilled-ticket-gate`: the first dispatch (`spinoff <ticket>`) of a ticket not tagged `spike` is refused, with nothing queued, when the ticket has no `## Drilled` section or no `## Done when` item, and when no `go` check is recorded on the ticket's current text, unless the dispatcher overrides it with `--no-check '<why>'`; a `spike` ticket is refused instead without `## Questions`, `## Box`, `## Done when` and a link to the ticket it serves (platform/cli-coord/src/spinoff-check.ts:352-399; `bun test test/spinoff-drilled-1980.test.ts test/spinoff-check-1825.test.ts` in platform/cli-coord passes).
- `critical-only-usage`: a `critical` priority ranks above urgent (stored as 6). Pacing follows the provider of route `builder.complex`'s first model (the local models file, then the last `model_routes` this machine read): `antigravity` reads `gemini-weekly` from T3 Code's local `~/.t3/caches/antigravity.json`, and anything else (including a missing or malformed models file) reads `seven_day` from `~/.t3/caches/claudeAgent.json` (`OB_USAGE_T3_CACHE` overrides the path); `checkedAt` reads `usageLimits.checkedAt` falling back to top-level `checkedAt`. While that weekly usage is 98% or more and its window has not reset, `next` lists only critical items after one line naming the provider (Gemini for Antigravity, Claude otherwise), usage and reset, and a dispatch, queue or send-back of a ticket that is not critical is refused with nothing queued or changed, unless overridden with `--over-usage '<why>'`, which is recorded on the ticket and refused from a T3 Code thread. A missing cache, no weekly window or a check older than 60 minutes reads as usage unknown, is said once on stderr and never blocks (apps/cli/src/usage-gate.ts, apps/cli/src/commands/usage.ts; `bun test test/usage-gate-os108.test.ts` in platform/cli-core and `bun test test/spinoff-usage-gate.test.ts` in platform/cli-coord pass).
- `parallel-conflict-checks`: a declared-file overlap warning. Before a dispatch launches, the ticket's declared files (its newest `go` check's sheets, directory and glob entries kept) are compared with every live spinoff row in the same repo, that row's declared files plus its pushed branch's `git diff --name-only origin/main...origin/<branch>` (its worktree when not pushed, else declared only). Each overlapping row prints `overlap: <ref> (#<row>) <paths>` and one `overlap` decision is recorded on the ticket, and the dispatch launches anyway; lockfiles are ignored, and with `--no-check` it prints `overlap: unknown, no recorded check`. `spinoff overlap <ticket> [--json]` prints the same lines without launching, over the API on a client (platform/cli-coord/src/spinoff-overlap.ts; `bun test test/spinoff-overlap-os47.test.ts` in platform/cli-coord passes).
- `agent-build-worktree`: a dispatch opens the builder in a git worktree on the ticket's own branch: it reuses the worktree already checked out on that branch, or else runs `git worktree add <path> -b <branch>` from `origin/main` (local `main` when the repo has no `origin/main` or its local `main` is ahead), and launches the builder as a T3 Code thread, the only launcher, so it needs T3 Code (platform/cli-coord/src/commands/spinoff.ts:1195-1209 and 1528-1536).
- `leases`: a lease on a resource such as `ticket:<ref>` or `worktree:<path>` has one live holder at a time, and a second holder is refused until it is released or expires (platform/cli-coord/src/lease.ts:175-189 and 466-467; `bun apps/cli/src/index.ts lease --help` lists `acquire`, `run` and `release` subcommands; `bun test test/lease.test.ts test/lease-tickets.test.ts` in platform/cli-coord passes).
- `review-merge-skills`: agent skills gate a builder's pull request before merge: `ob-skeptical-review` (read-only reviewers that presume every changed line is wrong; default legs are `neon` through `agy` and `opus` through `claude`, with `deepseek` and `luna` still runnable when named), `ob-babysit-pr` (the watch on a handed-off pull request) and `ob-land` (the builder opens the pull request, another role gates and merges it) (skills/README.md:46-48, apps/cli/src/models-file.ts, apps/cli/src/review-readers.ts, skills/ob-skeptical-review/review-leg.ts).
- `role-skills`: agent skills prime a thread for each role: `ob-architect` (plans, drills and dispatches every build, then gates and merges), `ob-sentinel` (verifies, merges and deploys every pull request) and `ob-muse` (explores and hands over a design once confirmed) (skills/README.md:39, 51 and 58).
- `role-runs`: `role start <team> <role>` keeps one T3 Code run per team role (architect, sentinel or muse): it reuses the open run while its thread is live; with no open run and a live seat thread for the role (bound by `t3 architect` or `t3 team restart`) it opens no run and uses the seat as it is, launching, pinning and moving nothing; and otherwise opens a new pinned thread on route `role.<role>` (its default is the active profile's `builder.complex` with a provider, else `claudeAgent:claude-opus-5-5`) at the model's default effort; `t3 architect|sentinel|muse` and `t3 team restart` (`ensureTeamThread`) open new role threads on route `role.<role>` when a models file or `model_routes` names it (else the T3 project's default model); `role status` and `role end` read and end a run. Each run is a row in `role_run`, whose partial unique index on (team, role) where `ended_at` is null keeps one open run (apps/cli/src/commands/role.ts, apps/cli/src/t3/dispatch.ts, apps/cli/src/role-run.ts; `bun test test/role-run.test.ts` in platform/cli-core and `bun test test/t3-dispatch.test.ts` in platform/cli-coord pass).
- `model-routes`: which model runs every use is one server setting, `model_routes`: routes (the builder set, `checker`, `role.architect|sentinel|muse`, `sweep.first`, `sweep.escalate`, `subagent.explore`, `subagent.fixup`, `job.<name>`) each with a fallback chain and an optional effort, grouped into profiles with one `active`. Each route resolves from this machine's `~/.config/ob/models.jsonc`, then the server, then the defaults (what ran before), and `ob models show` labels each `local`, `server` or `default`; `ob models get|set|unset|use|reader` read and write it, over the API on a client. The builder set is ranges of a 1-10 complexity score, `builder.<from>-<to>`, which must cover 1-10 with no gap and no overlap in each layer; the old `builder.simple|medium|complex` routes read as the ranges 1-3, 4-6 and 7-10, a layer mixing both forms is refused, and `role.*` and `job.*` take the range covering 8. A dispatch is scored with `--complexity 1-10` (5 when none is given; `--tier simple|medium|complex` is an alias for 2, 5 and 8 that prints a note, and both flags together exit 2), an urgent ticket runs at `max(score, 7)`, the score is stored on the spinoff row (SQLite and Postgres) and sent over the API (a tier-only client is accepted), `ob spinoff show` and `gateable` print `complexity N/10`, and `ob spinoff trial start --range a-b` pairs only scores in that range. A spinoff launch moves along the chain of the range covering its score only on a credit or quota error, recording `route <name>: <from> -> <to> (quota)` on the ticket's Decisions trail (apps/cli/src/model-routes.ts, apps/cli/src/commands/models.ts, platform/cli-coord/src/spinoff-credit.ts; `bun test test/model-routes-os145.test.ts test/complexity-ranges-os177.test.ts` in platform/cli-core and `bun test test/t3-dispatch.test.ts test/spinoff-urgent-tier.test.ts test/spinoff-trial-1991.test.ts` in platform/cli-coord pass).
- `models-page`: the OB dashboard (apps/ob-dashboard) has a Models tab at `/models` that shows every route of a profile (each fixed route and the profile's `job.<name>` routes) with its chain, effort and `local`, `server` or `default` label, and edits the server's `model_routes`: a route's chain and effort, unset, review readers (add, change, remove) and their tiers, and the active profile. Above the review readers it shows the OpenCode Go credit state (ok, running low, failed, or not checked yet) and the time of the last recorded `ob creds check opencode-go` (with its recorded detail when it is not ok), read from the store and never from the provider. A route this host's models file overrides shows `local` and the file's path, and the file is never edited from the page. Saves go through the same validation as `ob models`, are refused over plain http to a non-loopback host and from another site, and `ob models show` reads them as `server` (platform/dashboard-kit/src/server/model-routes.ts, apps/ob-dashboard/src/routes/models.tsx, apps/ob-dashboard/src/lib/credit.ts; `bun test test/model-routes.test.ts` in platform/dashboard-kit passes, and `ob lease run cpu:browser -- bunx moon run ob-dashboard:e2e` passes in Chromium on desktop and phone).
- `dashboard-home`: the OB dashboard's header nav lists Home, Queue, Alerts, Tokens, Models and Timeline with the current page marked (in the Menu at phone width). Its home at `/` shows "To review" (the builders whose status is `needs-human` or `manual-review`) and the ranked focus (open items with a Today rank, in rank order), each with an empty state and updated by the live snapshot. A row opens the item in the shared item drawer, whose start, ready, block, close, reopen and Today rank save to the store through the same guarded writes as the Today page (apps/ob-dashboard/src/routes/index.tsx, apps/ob-dashboard/src/server/items.ts, apps/ob-dashboard/src/components/ObFrame.tsx; `bun test test/ob-frame.test.tsx` in apps/ob-dashboard passes, and `ob lease run cpu:browser -- bunx moon run ob-dashboard:e2e` passes in Chromium on desktop and phone).
- `dashboard-queue`: the OB dashboard has a Queue page at `/queue?project=<slug>` (omnislash when none is named, with a project picker) that lists one project's open items in `ob next --project <slug>` order, under a heading per priority (critical, urgent, flake, high, medium, low, none) with its count, an empty one shown as a "Drop here" row. Items ranked into Today keep their place in their band and carry a Today mark. Each row shows its ref, title, priority, a status pill when it is not plain open, and its tags; its ref opens the shared item drawer. A drag (pointer, or from the keyboard by the row's grip) inside a band changes the queue order only; into another band, or onto an empty one, it takes that band's priority, the same move `ob order` makes. The row's priority picker sets the priority. A change from the CLI shows up without a reload through the live snapshot (platform/dashboard-kit/src/server/queue.ts, apps/ob-dashboard/src/routes/queue.tsx, apps/ob-dashboard/src/server/items.ts; `bun test test/queue.test.ts` in platform/dashboard-kit passes, and `ob lease run cpu:browser -- bunx moon run ob-dashboard:e2e` passes in Chromium on desktop and phone).
- `dashboard-timeline`: the OB dashboard has a read-only Timeline page at `/timeline?project=<slug>&from=&to=` (omnislash and the last 7 days when none is given; 7, 30 and 90 day presets or a custom from and to, all in the URL). Tiles show Opened, Closed, Net (opened minus closed) and the median cycle of tasks closed in the range; a weekly table shows Opened, Closed, Net, Blocks (spells started that week) and Median cycle. The feed lists the project's ticket transitions and priority changes grouped by UTC day, newest first, 200 lines a page with "Load older": a close from blocked is one Closed line carrying the blocked spell, a spinoff row's build steps fold to one "built, row N, X h" line shown only with the Builds switch, and a landed row with a `pr_url` shows "merged, PR #N" (apps/ob-dashboard/src/lib/timeline.ts, apps/ob-dashboard/src/server/timeline.ts, apps/ob-dashboard/src/routes/timeline.tsx; `bun test test/timeline.test.ts` in apps/ob-dashboard passes, and `ob lease run cpu:browser -- bunx moon run ob-dashboard:e2e` passes in Chromium on desktop and phone).
- `priority-trail`: a change to an item's stored priority, by `edit --priority`, by an `order` move into another band or from the OB dashboard, records one `priority_change` event (from, to, actor and an optional `--note`) on the item's Decisions trail in the same transaction, and `show` prints it as `priority <from> → <to>`; setting the same value records nothing, and a priority given at `add` is not recorded. `block --owner <who>` keeps the owner as `block_owner` on the blocked transition (apps/cli/src/items.ts, apps/cli/src/decisions.ts, apps/cli/src/workflow.ts; `bun test test/priority-trail-os26.test.ts` in platform/cli-core and `bun test test/priority-trail-pg-os26.test.ts` in platform/cli-db pass).
- `role-inbox`: `send <team> <role> "<text>"` stores a message for a team role (architect, sentinel or muse) in `role_message` on the server, and `inbox <team> <role>` lists the unread ones oldest first, `--all` every one, and `--read <id>... --by <id>` marks them read; a role that is not the architect and not bound on the team is refused and nothing is stored. A builder's handoff stores its readying note there too, one row per commit, without ever blocking the handoff, and closing the ticket withdraws its unread handoff rows (apps/cli/src/inbox.ts, apps/cli/src/commands/inbox.ts; `bun test test/inbox.test.ts` in platform/cli-core passes, locally and over the API, and `bun test test/inbox-handoff.test.ts` in platform/cli-coord passes).
- `role-delivery`: `send` then delivers the role's unread messages into its run: queued into the open run's thread when that run is on this machine's T3, else into the role's live seat thread when it has one and no open run, marked read by `seat:<role>-<team>`, else it starts a run (as `role start`) whose brief lists them; a run open on another machine's T3 gets nothing and the message stays unread. Delivered messages are marked read by `role-run-<id>`, and `--no-deliver` only stores. A builder's handoff delivers its stored note the same way, to the sentinel, else the architect, and falls back to the seat thread only when the inbox write fails (apps/cli/src/role-deliver.ts; `bun test test/role-deliver.test.ts` in platform/cli-core passes, locally and over the API, and `bun test test/inbox-handoff.test.ts` in platform/cli-coord passes).
- `role-brief`: `role brief <team> <role>` prints what a fresh role run needs, computed from the store: the team and its projects' stages, pacing from route `builder.complex`'s provider's weekly window in the local T3 cache (`gemini-weekly` in `antigravity.json` for Antigravity, `seven_day` in `claudeAgent.json` otherwise), rows in flight, handed-off rows to gate, the unread inbox, open asks for the owner, the next three buildable items in `ob next` order, the skill to load, and the note the last run left with `role note`, which is capped at 40 lines and 4000 characters and shown once; `role start` seeds a new run with the brief (apps/cli/src/role-brief.ts, apps/cli/src/commands/role.ts; `bun test test/role-brief.test.ts` in platform/cli-core passes, locally and over the API).
- `role-tick`: `role tick` writes what needs each team's architect into its inbox, one message per finding, and delivers it as `send` does: a T3 builder whose heartbeat is over 60 minutes old, a flake ticket with no builder on it, and a team project with nothing in flight whose top item would dispatch today. An unchanged finding writes nothing again, a pass with no unread message delivers nothing and starts no run, and while the good-night lock file holds a future time it writes but starts and sends nothing. `daemon install` installs it as a client job every 15 minutes (a systemd user timer on Linux, a launchd job on macOS) (apps/cli/src/role-tick.ts, apps/cli/src/commands/role-tick.ts; `bun test test/role-tick.test.ts` in platform/cli-core passes, locally and over the API, and `bun test test/daemon-linux-664.test.ts` in platform/cli-coord passes).
- `role-end`: `role tick` also ends a team's open role runs on this machine's T3 when they are done: a run with nothing for 15 minutes after its last turn, or whose context (read from T3 Code's own state database) has reached 200,000 tokens, is asked to write its successor note with `role note`, then its thread is settled and the run ended, freeing its lease. A turn in flight, a question waiting on the owner or a message queued in the thread keeps it open, and a run that writes no note within 10 minutes is kept (apps/cli/src/role-end.ts, apps/cli/src/commands/role-tick.ts; `bun test test/role-end.test.ts` in platform/cli-core passes).
- `compared-linear`: Linear ships agents on issues: an issue is delegated by assigning it to Linear's own agent or an installed third-party agent, and Linear's agent writes code in a sandbox and creates branches (https://linear.app/docs/agents-in-linear, https://linear.app/docs/assigning-issues and https://linear.app/changelog, read 2026-11-18). Those pages name no check on what an issue says before it is delegated; OmniSlash refuses the first dispatch of a ticket that has no drilled section, no done-when item or no recorded check, unless overridden, as `drilled-ticket-gate` says (platform/cli-coord/src/spinoff-check.ts:352-399). OmniSlash makes no other claim beyond what Linear ships.
- `compared-jira`: Jira ships Rovo agents on work items, in beta: an agent is added to the assignee field, mentioned in a comment, or set on a workflow transition or board column, and the Rovo Dev coding agent has a CLI worktree mode that creates a branch (https://support.atlassian.com/rovo/docs/collaborate-with-your-rovo-agent-on-work-items/ and https://support.atlassian.com/rovo/docs/use-worktree-mode-in-rovo-dev-cli/, read 2026-11-18). Those pages name no check on what a work item says before an agent takes it; OmniSlash refuses the first dispatch of a ticket that has no drilled section, no done-when item or no recorded check, unless overridden, as `drilled-ticket-gate` says (platform/cli-coord/src/spinoff-check.ts:352-399). OmniSlash makes no other claim beyond what Jira ships.
- `scoped-api-token`: `ob api-token add <user> --project <p>[,<p>...]` prints a token once and stores only its sha256 in `~/.ob_api_tokens.json` (`OB_API_TOKENS_FILE` moves it, mode 0600 or every scoped token is refused with the path named); the API re-reads the file per request, and a scoped token may only GET `/items`, `/items/<ref>`, `/next`, `/search` and `/projects`, filtered to its projects (an item outside them is 404), while every other route, method or unknown path is 403 `forbidden` (apps/cli/src/api/scoped-tokens.ts, platform/cli-core/test/api-scoped-token-178.test.ts).
- `public-repo`: the source is public at https://github.com/slashsuite/omnislash (`gh repo view slashsuite/omnislash --json visibility` reads `PUBLIC`).

## Where it runs
- `checkout-linux`: a fresh clone with Bun 1.4.2 runs `bun install`, then `bun apps/cli/src/index.ts --help` (checked on Linux).
- `role-api-base`: when `OMNISLASH_ROLE_API` or the first line of `~/.omnislash_role_api_url` names a base url (`OMNISLASH_ROLE_API_URL_FILE` moves the file), the team role routes (`/teams/:name/runs`, `brief`, `notes`, `tick`, `inbox` and their sub-paths) go to that server and every other route stays on `OMNISLASH_API`; unset, every route goes to `OMNISLASH_API` as before (apps/cli/src/api/client.ts `ROLE_ROUTE`, apps/cli/src/api/config.ts; `bun test test/api-role-base.test.ts` in apps/cli passes).
