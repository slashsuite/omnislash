# OmniSlash facts

Checked against main at adad1dc on 2026-11-19.

## What it is
OmniSlash is a command-line tool for keeping track of tickets, projects and the agents that work on them.
It is in alpha, so anything may change or break.

## Today
- `help-command`: `bun apps/cli/src/index.ts --help` prints the command reference from a checkout of main.
- `item-tracking`: with `OMNISLASH_STORE=sqlite`, `OMNISLASH_DB_CREATE=1` and `OMNISLASH_DB` set to a new path, `bun apps/cli/src/index.ts add "<title>" --project <name> --kind side` and `list` create and list work items in that new SQLite file. Postgres is the default store and needs a connection URL.
- `drilled-ticket-gate`: the first dispatch (`spinoff <ticket>`) of a ticket not tagged `spike` is refused, with nothing queued, when the ticket has no `## Drilled` section or no `## Done when` item, and when no `go` check is recorded on the ticket's current text, unless the dispatcher overrides it with `--no-check '<why>'`; a `spike` ticket is refused instead without `## Questions`, `## Box`, `## Done when` and a link to the ticket it serves (platform/cli-coord/src/spinoff-check.ts:352-399; `bun test test/spinoff-drilled-1980.test.ts test/spinoff-check-1825.test.ts` in platform/cli-coord passes).
- `agent-build-worktree`: a dispatch opens the builder in a git worktree on the ticket's own branch: it reuses the worktree already checked out on that branch, or else runs `git worktree add <path> -b <branch>` from `origin/main` (local `main` when the repo has no `origin/main` or its local `main` is ahead), and launches the builder as a T3 Code thread, the only launcher, so it needs T3 Code (platform/cli-coord/src/commands/spinoff.ts:1195-1209 and 1528-1536).
- `leases`: a lease on a resource such as `ticket:<ref>` or `worktree:<path>` has one live holder at a time, and a second holder is refused until it is released or expires (platform/cli-coord/src/lease.ts:175-189 and 466-467; `bun apps/cli/src/index.ts --help` lists `lease acquire`, `lease run` and `lease release`; `bun test test/lease.test.ts test/lease-tickets.test.ts` in platform/cli-coord passes).
- `review-merge-skills`: agent skills gate a builder's pull request before merge: `ob-skeptical-review` (read-only reviewers that presume every changed line is wrong), `ob-babysit-pr` (the watch on a handed-off pull request) and `ob-land` (the builder opens the pull request, another role gates and merges it) (skills/README.md:46-48).
- `role-skills`: agent skills prime a thread for each role: `ob-architect` (plans, drills and dispatches every build, then gates and merges), `ob-sentinel` (verifies, merges and deploys every pull request) and `ob-muse` (explores and hands over a design once confirmed) (skills/README.md:39, 51 and 58).
- `role-runs`: `role start <team> <role>` keeps one T3 Code run per team role (architect, sentinel or muse): it reuses the open run while its thread is live; with no open run and a live seat thread for the role (bound by `t3 architect` or `t3 team restart`) it opens no run and uses the seat as it is, launching, pinning and moving nothing; and otherwise opens a new pinned thread on claude-opus-5-5 at the model's default effort; `role status` and `role end` read and end it. Each run is a row in `role_run`, whose partial unique index on (team, role) where `ended_at` is null keeps one open run (apps/cli/src/commands/role.ts, apps/cli/src/role-run.ts; `bun test test/role-run.test.ts` in platform/cli-core passes, locally and over the API).
- `role-inbox`: `send <team> <role> "<text>"` stores a message for a team role (architect, sentinel or muse) in `role_message` on the server, and `inbox <team> <role>` lists the unread ones oldest first, `--all` every one, and `--read <id>... --by <id>` marks them read; a role that is not the architect and not bound on the team is refused and nothing is stored. A builder's handoff stores its readying note there too, one row per commit, without ever blocking the handoff, and closing the ticket withdraws its unread handoff rows (apps/cli/src/inbox.ts, apps/cli/src/commands/inbox.ts; `bun test test/inbox.test.ts` in platform/cli-core passes, locally and over the API, and `bun test test/inbox-handoff.test.ts` in platform/cli-coord passes).
- `role-delivery`: `send` then delivers the role's unread messages into its run: queued into the open run's thread when that run is on this machine's T3, else into the role's live seat thread when it has one and no open run, marked read by `seat:<role>-<team>`, else it starts a run (as `role start`) whose brief lists them; a run open on another machine's T3 gets nothing and the message stays unread. Delivered messages are marked read by `role-run-<id>`, and `--no-deliver` only stores. A builder's handoff delivers its stored note the same way, to the sentinel, else the architect, and falls back to the seat thread only when the inbox write fails (apps/cli/src/role-deliver.ts; `bun test test/role-deliver.test.ts` in platform/cli-core passes, locally and over the API, and `bun test test/inbox-handoff.test.ts` in platform/cli-coord passes).
- `role-brief`: `role brief <team> <role>` prints what a fresh role run needs, computed from the store: the team and its projects' stages, pacing from the local T3 cache's seven-day window, rows in flight, handed-off rows to gate, the unread inbox, open asks for the owner, the next three buildable items in `ob next` order, the skill to load, and the note the last run left with `role note`, which is capped at 40 lines and 4000 characters and shown once; `role start` seeds a new run with the brief (apps/cli/src/role-brief.ts, apps/cli/src/commands/role.ts; `bun test test/role-brief.test.ts` in platform/cli-core passes, locally and over the API).
- `role-tick`: `role tick` writes what needs each team's architect into its inbox, one message per finding, and delivers it as `send` does: a T3 builder whose heartbeat is over 60 minutes old, a flake ticket with no builder on it, and a team project with nothing in flight whose top item would dispatch today. An unchanged finding writes nothing again, a pass with no unread message delivers nothing and starts no run, and while the good-night lock file holds a future time it writes but starts and sends nothing. `daemon install` installs it as a client job every 15 minutes (a systemd user timer on Linux, a launchd job on macOS) (apps/cli/src/role-tick.ts, apps/cli/src/commands/role-tick.ts; `bun test test/role-tick.test.ts` in platform/cli-core passes, locally and over the API, and `bun test test/daemon-linux-664.test.ts` in platform/cli-coord passes).
- `role-end`: `role tick` also ends a team's open role runs on this machine's T3 when they are done: a run with nothing for 15 minutes after its last turn, or whose context (read from T3 Code's own state database) has reached 200,000 tokens, is asked to write its successor note with `role note`, then its thread is settled and the run ended, freeing its lease. A turn in flight, a question waiting on the owner or a message queued in the thread keeps it open, and a run that writes no note within 10 minutes is kept (apps/cli/src/role-end.ts, apps/cli/src/commands/role-tick.ts; `bun test test/role-end.test.ts` in platform/cli-core passes).
- `compared-linear`: Linear ships agents on issues: an issue is delegated by assigning it to Linear's own agent or an installed third-party agent, and Linear's agent writes code in a sandbox and creates branches (https://linear.app/docs/agents-in-linear, https://linear.app/docs/assigning-issues and https://linear.app/changelog, read 2026-11-18). Those pages name no check on what an issue says before it is delegated; OmniSlash refuses the first dispatch of a ticket that has no drilled section, no done-when item or no recorded check, unless overridden, as `drilled-ticket-gate` says (platform/cli-coord/src/spinoff-check.ts:352-399). OmniSlash makes no other claim beyond what Linear ships.
- `compared-jira`: Jira ships Rovo agents on work items, in beta: an agent is added to the assignee field, mentioned in a comment, or set on a workflow transition or board column, and the Rovo Dev coding agent has a CLI worktree mode that creates a branch (https://support.atlassian.com/rovo/docs/collaborate-with-your-rovo-agent-on-work-items/ and https://support.atlassian.com/rovo/docs/use-worktree-mode-in-rovo-dev-cli/, read 2026-11-18). Those pages name no check on what a work item says before an agent takes it; OmniSlash refuses the first dispatch of a ticket that has no drilled section, no done-when item or no recorded check, unless overridden, as `drilled-ticket-gate` says (platform/cli-coord/src/spinoff-check.ts:352-399). OmniSlash makes no other claim beyond what Jira ships.

## Where it runs
- `checkout-linux`: a fresh clone with Bun 1.4.2 runs `bun install`, then `bun apps/cli/src/index.ts --help` (checked on Linux).
- `role-api-base`: when `OMNISLASH_ROLE_API` or the first line of `~/.omnislash_role_api_url` names a base url (`OMNISLASH_ROLE_API_URL_FILE` moves the file), the team role routes (`/teams/:name/runs`, `brief`, `notes`, `tick`, `inbox` and their sub-paths) go to that server and every other route stays on `OMNISLASH_API`; unset, every route goes to `OMNISLASH_API` as before (apps/cli/src/api/client.ts `ROLE_ROUTE`, apps/cli/src/api/config.ts; `bun test test/api-role-base.test.ts` in apps/cli passes).
